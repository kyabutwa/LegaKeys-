# LEGAKEYS — PLATFORM FOUNDATION UX

## 01 — Design target

LegaKeys should feel like a **mature operating system for life, places, services and work** — not a property-management portal, a generic SaaS dashboard, or a collection of disconnected mini-apps.

The experience combines:

- the calm hierarchy and adaptive materials of **Apple iOS 26**
- the conversational, structured and task-oriented interaction model demonstrated by **OpenAI**
- the workflow depth and governed enterprise execution of **ServiceNow**
- the spatial and operational intelligence of smart-building and smart-city platforms
- the clarity and restraint expected from a modern premium mobile product

The result must remain distinctly **LegaKeys**.

**Visual inspiration is not visual cloning.** Borrow principles, not proprietary screens, assets or branding.

## 03 — Apple iOS 26 / Liquid Glass influence

Apple's iOS 26 design introduces **Liquid Glass**, an adaptive translucent material that dynamically responds to content and context. Apple also redesigned controls, navigation, tab bars and sidebars to behave as a distinct functional layer above content. citeturn0search0

LegaKeys should take the underlying principles:

### Adopt

- layered depth
- adaptive surfaces
- restrained translucency
- content-first layouts
- controls that float above content when useful
- navigation that recedes while content takes focus
- rounded geometry aligned with modern device surfaces
- motion that communicates hierarchy and state
- light/dark adaptation
- strong typography
- generous spacing
- clear grouping

### Do not copy

- Apple's exact Liquid Glass appearance
- Apple icons
- Apple navigation layouts
- Apple branding
- proprietary visual assets
- decorative glass effects without functional purpose

### LegaKeys material language

**LegaKeys Depth**

1. **Foundation** — deep navy environment
2. **Content surface** — high-contrast white / near-white content
3. **Elevated surface** — restrained translucent or elevated card
4. **Focused surface** — active task / decision layer
5. **Modal surface** — consequential confirmation or detailed workflow

Glass/translucency is optional and functional. It must never reduce readability.

## 04 — OpenAI influence: structured intelligence UI

OpenAI's current UI guidance recommends choosing the smallest presentation that completes the task, using inline cards for focused results, carousels for small visual collections, and fullscreen views for rich workflows. It also explicitly recommends limiting primary actions and avoiding nested scrolling and deep navigation inside cards. citeturn0search1turn0search2

LegaKeys adopts this as a **structured intelligence rule**.

### Constantyna response hierarchy

A response should normally follow:

**TITLE**

One-line understanding.

**CONTEXT**

Where / when / why it matters.

**RESULT**

The actual answer, state or recommendation.

**NEXT ACTION**

One primary action.

**SECONDARY**

Optional supporting action.

**EVIDENCE / STATUS**

Only when relevant.

Example:

> **Maintenance request**
>
> Water leak reported for Unit 4B.
>
> **Status:** Requires review  
> **Context:** Tsavo · Building 2 · Unit 4B
>
> **Next:** Review request
>
> Evidence available

The assistant should not bury the result inside a paragraph.

### Card rules

- one clear purpose per card
- one primary CTA
- at most one secondary CTA
- no nested cards unless hierarchy genuinely requires it
- no nested scrolling
- no miniature applications inside cards
- no unnecessary tabs inside cards
- short titles
- concise metadata
- expandable detail only when useful
- fullscreen for complex workflows

## 05 — ServiceNow influence: operational UX

ServiceNow's AI Experience positions a unified, context-aware interface across people, data and workflows with governance and security built into the platform. citeturn0search3

Every meaningful operation should make these understandable:

**WHAT**

**WHERE**

**WHO**

## 08 — Floating-card system

Floating cards are a **hierarchy mechanism**, not decoration.

### Level 0 — Background

Deep navy platform environment.

### Level 1 — Base content

Primary content flows naturally with minimal containers.

### Level 2 — Floating card

Used for:

- important status
- current task
- service result
- contextual recommendation
- quick action

### Level 3 — Focus card

Used for:

- authorization decision
- payment confirmation
- access decision
- incident response
- critical review

### Level 4 — Fullscreen workflow

Used for:

- maps
- digital-twin exploration
- complex work orders
- multi-step booking
- rich evidence review
- advanced workspace operations

### Card geometry

- generous corner radius
- subtle depth
- strong internal spacing
- clear title
- short supporting text
- explicit state
- one obvious action
- no visual clutter

### Card rule

**A card must answer one question or enable one meaningful decision.**

## 18 — Authorization UX

Authorization must be understandable without exposing implementation complexity.

For consequential actions, show:

**Action**

What will happen?

**Scope**

Where / what does it affect?

**Actor**

Who is acting?

**Authority**

Why is this actor allowed?

**Conditions**

What limits apply?

**Time**

When does authorization apply?

**Result**

What happened?

For sensitive actions, confirmation should be explicit.

### Never

- “Face recognized → door opened”
- “Admin → automatically allowed”
- “Team member → automatically authorized”
- “AI recommended → automatically executed”

### Correct

**Credential signal → BeatAccess → Context + Capability + Authority + Conditions → Decision → Action**

## 25 — State design

The UI must distinguish:

**Loading**

The platform has not resolved the state yet.

**Unknown**

The platform lacks sufficient evidence.

**Unavailable**

A required service/system is unavailable.

**Pending**

The request exists but has not completed.

**Denied**

Authorization was not granted.

**Failed**

Execution attempted and failed.

**Expired**

A previously valid authorization/state is no longer valid.

**Revoked**

A previously valid authorization was explicitly withdrawn.

**Completed**

A real completion event exists.

These states must never be collapsed into one generic error/success treatment.

## 28 — Mature UX quality gate

A Platform Foundation UX surface is not complete until it passes:

### Visual

- no invisible text
- no low-contrast text
- no clipped content
- no distorted logo
- no uncontrolled gradients
- no unnecessary decoration
- consistent spacing
- consistent card geometry
- clear typography

### Interaction

- one obvious primary action
- predictable navigation
- visible current context
- progressive disclosure
- recoverable errors
- explicit consequential actions
- no accidental destructive action

### Truth

- no fake data
- no fake availability
- no fake provider connection
- no fake transaction success
- no invented live state
- explicit UNKNOWN where evidence is insufficient

### Governance

- authentication ≠ authorization
- capability ≠ authority
- relationship ≠ authority
- biometric recognition ≠ authorization
- workspace visibility ≠ authority
- AI recommendation ≠ authorization

### Platform

- one identity model
- one context model
- one authorization model
- one event model
- one evidence model
- one Digital Twin
- one service state model
- one intelligence boundary
